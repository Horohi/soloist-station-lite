# Анализ и устранение сброса диалога Алисы при повторных командах (soloist-bridge)

## 📌 Суть проблемы
После голосовых команд управления воспроизведением («Алиса, стоп», «пауза», «следующий», «включи Х») при быстром повторном вызове («Алиса...») кольцо подсветки на колонке кратковременно вспыхивает (на 100–200 мс) и тут же гаснет, не давая пользователю сказать фразу. Команда срабатывает только на второй вызов. Это создавало иллюзию «колонка игнорирует ровно каждый второй вызов».

---

## 🔍 Архитектура состояний Quasar (`VoiceState.mode`)

В бинарном IPC-протоколе Яндекс.Станции поле 1 (`alice_state` / `mode`) сообщения `VoiceState` принимает следующие значения:
* **`0` — IDLE:** Покой (микрофон ждет споттер, кольцо не горит, TTS молчит).
* **`1` — LISTENING:** Сработало ключевое слово «Алиса» (KWS/VAD), зажглась подсветка, аудиопоток с микрофонов пишется и отправляется на распознавание.
* **`2` — PROCESSING:** Пользователь закончил фразу, облако Megamind обрабатывает запрос.
* **`3` — SPEAKING:** Алиса отвечает голосом через TTS или запускает встроенный плеер Яндекс.Музыки.

---

## 🐛 Причина бага в коде `src/soloist-bridge.c`

При распознавании любой команды мост взводит таймер супрессии Алисы на **3–5 секунд** (`cancel_alice_until_ms = now + 5000`), чтобы облачный ответ Яндекса («Включаю трек», «Останавливаю») не накладывался на Spotify.

При этом в цикле обработки IPC стояло условие:
```c
if (find_field(state_payload, state_len, 1, 0, 0, 0, &alice_state) &&
    alice_state != 0 && now < cancel_alice_until_ms) {
    send_cancel_alice(quasar_fd);
}
```

Поскольку при новом вызове колонка переходит в `alice_state = 1` (LISTENING), условие `1 != 0 && now < cancel_alice_until_ms` оказывалось истинным в течение 3–5 секунд после предыдущей команды. Бридж **моментально убивал новый входящий диалог** директивой `send_cancel_alice`.

---

## 🛠️ Решение

```c
if (voice_state_payload(frame_body, frame_len, &state_payload, &state_len)) {
    uint64_t alice_state = 0;
    if (find_field(state_payload, state_len, 1, 0, 0, 0, &alice_state)) {
        if (alice_state == 1) {
            // Пользователь сказал «Алиса» (wake-word): мгновенно сбрасываем окно супрессии,
            // чтобы диалог не глушился и Алиса слушала фразу.
            cancel_alice_until_ms = 0;
        } else if ((alice_state == 2 || alice_state == 3) && now < cancel_alice_until_ms) {
            // Глушим только обработку/TTS-ответ облака Яндекса на перехваченную Spotify-команду
            send_cancel_alice(quasar_fd);
        }
    }
}
```

## 🔬 Анализ сценариев и доказательство отсутствия регрессий

### Сценарий 1: Пользователь говорит «Алиса, стоп» (или «пауза»)
1. **Фаза речи:** Пользователь говорит *«Алиса, стоп»*. При входе в режим слушания `alice_state = 1` сбрасывает `cancel_alice_until_ms = 0` (но отмена не шлется, микрофон открыт).
2. **Фаза распознавания:** Приходит финальный результат ASR: `final == 1`, текст `"стоп"`.
   * Функция `handle_voice_recognition` перехватывает фразу.
   * `run_soloist_cmd("pause")` ставит Spotify на паузу.
   * `trigger_alice_suppression(quasar_fd, 3000)`:
     * Пакет `send_cancel_alice` (`CANCEL_DIALOG`, `STOP_CONVERSATION`, `STOP_TTS`) отправляется немедленно.
     * Взводится окно супрессии: `cancel_alice_until_ms = now + 3000`.
3. **Поведение Алисы:** 
   * Quasar получает отмену и глушит диалог.
   * Если облако с запозданием шлет голосовой ответ — Quasar переходит в `alice_state = 2` или `3`. Ветка `else if ((alice_state == 2 || alice_state == 3) && now < cancel_alice_until_ms)` повторно отправляет `send_cancel_alice`, гарантированно глуша TTS.

### Сценарий 2: Пользователь через 1–2 секунды после «стоп» дает новую команду
* Пользователь говорит: *«Алиса...»*. Quasar переходит в `alice_state = 1`.
* Ветка `if (alice_state == 1) cancel_alice_until_ms = 0;` мгновенно аннулирует таймер супрессии, отмена не вызывается.
* Подсветка горит штатно, Quasar слушает фразу до конца.
* Если это команда Spotify (*«включи Х»*) — мост перехватывает ее и взводит новый таймер. Если бытовой вопрос к Алисе (*«какая погода»*) — мост его игнорирует, и Алиса спокойно отвечает голосом.

## 📊 Матрица граничных случаев (Corner Cases)

| Граничный случай | Поведение в коде | Риск регрессии |
| :--- | :--- | :--- |
| **1. Ложное срабатывание споттера (шум принят за «Алиса»)** | `alice_state` кратковременно становится `1`. Сбрасывается `cancel_alice_until_ms`. Колонка слушает тишину и уходит в `IDLE (0)`. На Soloist это не влияет. | **Нулевой** |
| **2. Голосовой ответ Алисы (TTS) пытается прорваться поверх музыки** | Голос Алисы — это строго `alice_state = 3`. Он попадает во вторую ветку `(alice_state == 2 || alice_state == 3)` и надежно глушится в окне супрессии. | **Нулевой** |
| **3. Порядок следования пакетов IPC** | Сначала парсится `voice_state_payload`, затем `voice_request_read`. При финальном распознавании статус в Quasar — `mode = 2` (PROCESSING), а не `1`. Поэтому `trigger_alice_suppression` взводит таймер **после** `alice_state = 1`, окно супрессии не сбрасывается раньше времени. | **Нулевой** |
| **4. Взаимодействие с дедупликатором `voice-request.h`** | Модуль дедупликации работает автономно по полю 7 (`request_id`) и флагу `final == 1`. Логика сброса `cancel_alice_until_ms` не влияет на кэш запросов. | **Нулевой** |
| **5. Аппаратные кнопки и сенсор** | При удержании центральной кнопки в коде уже было зашито `cancel_alice_until_ms = 0` (строка 1825). Фикс распространил это же естественное правило на голосовой вызов. | **Полная консистентность** |
